02 · Anatomy

Six parts, one job.

loop — the turn cycle

Model call, tool run, observation, repeat. It ends when the model stops or a turn limit fires.

~1:30. Ten seconds a part, one example each. Loop: OpenAI's function-calling flow is five steps — send tools, receive a call, run it in your application, send the output back, receive the next response; the Agents SDK repeats that until final output or max_turns. Tools: Anthropic's SWE-bench team spent more time optimizing tools than the overall prompt, and requiring absolute filepaths fixed a recurring failure. Context: Claude Code sends the full conversation with every request, so the window is a harness budget. Memory: Claude Code re-injects CLAUDE.md and auto memory from disk after compaction. Evals: SWE-bench scores a task only when the tests pass, so the number is execution, not opinion. Guardrails: Codex separates the sandbox (technical boundary) from the approval policy (when the agent must stop and ask).

The point: each part is owned, testable, and has failure modes. None of them is "the model". Next, one turn in sequence.

03 · Why they fail

Four ways a good model fails.

Symptom

Sharp early. Deep into the run, it contradicts its own decision.

Cause

Every token competes for attention; recall fades as the window fills.

Harness fix

Compact the history, clear stale tool output, load files on demand.

Symptom

The same tool twice, or the near-identical one beside it.

Cause

Overlapping tools create ambiguous choices and eat the window.

Harness fix

Fewer tools, one verb each, named for what they return.

Symptom

It reports done. The trace shows that no check ran.

Cause

With no check, looks done is the only stop signal it has.

Harness fix

A verify step that returns pass or fail, inside the loop.

Symptom

A new session walks back into last week's dead end.

Cause

State lives in the window, and the window is discarded.

Harness fix

Notes on disk, read at start, small enough to be read.

~1:15. Four ways the same good model fails, and each one is a harness part, not a model part. Context rot: Anthropic's context engineering post (29 Sep 2025) states that as the number of tokens in the window increases, the model's ability to recall information from that context decreases, across all models. The tell in a trace is a file re-read that was already read, or a decision reversed late in the run.

Tool sprawl: the same post calls bloated tool sets that overlap in function "one of the most common failure modes we see", because the model faces ambiguous decision points about which tool applies. The tell is a failed call followed immediately by a near-identical call to a sibling tool.

Silent success: Anthropic's Claude Code best practices say it plainly — "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." The tell is a final message that claims the tests pass, with no test command anywhere in the trace.

No memory: the context post recommends structured note-taking precisely because state held only in the window is lost across dozens of tool calls. The tell is a repeat of last session's dead end, discovered at the same cost.

03 · Why they fail

Same task. Two harnesses.

One tool. No scope, no check, no exit condition.

// the whole interface: one tool, no rules
{
  "name": "shell",
  "description": "Run any command.",
  "input_schema": { "command": "string" }
}

// loop: run it, append output, repeat until "done"
done No check ran. The word is the only evidence.

Three scoped tools. One verify gate it cannot skip.

// three tools, one verb each
read(path, range)     // read-only
edit(path, old, new)  // exact match or fail
verify(cmd)           // exit code is the truth

// loop: plan -> act -> verify
// verify fails: read the error, fix, verify again
passes, verified Exit 0 recorded in the trace.

The model is identical in both runs. Only the tool schema and the loop changed.

~1:15. Same task, same model, same repository. The before run gets one general shell and a loop that stops when the model says it is done. The after run gets three tools, each with one job, plus an explicit verify call whose exit code the loop can read.

The before trace is the one you have seen: a long chain of shell calls, a plausible patch, and a confident final message. Nothing false was said. Nothing was checked either, so a wrong patch and a right patch leave identical traces and identical cost. That is why the failure survives review — the harness had no opinion about truth.

The after trace costs one more step and produces a pass or fail the loop can act on. This is the claim from Anthropic's Claude Code guidance: give the model a check it can run and "the loop closes on its own"; without one, "you become the verification loop".

Nothing in either block is model code. It is harness code, and it is the part we own.

03 · Why they fail

Scaffolding moves the number.

SWE-bench Lite, 300 tasks · GPT-4 Turbo in all four runs · Yang et al., SWE-agent, NeurIPS 2024 (Tables 1 and 3)

Same model: 2.7% to 18.0% resolved. Third bar is that agent with its edit linter removed.

~1:30. This is the same model four times. GPT-4 Turbo, SWE-bench Lite, 300 real GitHub issues, scored by the repository's own tests. The only thing that changes across the bars is the interface and the loop around the model.

With the model reading retrieved files and writing a patch in one shot, 2.67% resolve. Give it a plain Linux shell and let it work interactively, 11.00%. Give it purpose-built tools — a file viewer with line numbers, a search that summarises, an editor that refuses edits that do not apply — 18.00%. The paper reports that as a 64% relative increase over the shell-only agent, same model.

The fourth comparison is the one I care about: take the full agent and remove only the linter on edits. 15.0%. The agent still reads, still searches, still edits. One harness check that returns a signal costs three points.

What this does not prove: it is one model from 2024, one benchmark, 300 tasks, and the authors report that per-instance results move between runs even when the average holds. It does not prove a gain of the same size transfers to our repository. Nothing in a public benchmark is our codebase.

Which is the point of the next slide: if the number moves this much on someone else's repo, you cannot tune a harness for yours without measuring yours.

~1:15. Public benchmarks measure a model against someone else's repository. SWE-bench Verified is a 500-task subset of SWE-bench, reviewed by humans so each task is solvable (Anthropic, "Raising the bar on SWE-bench Verified", Jan 2025). By early 2026 that benchmark is near saturation above 80% (Anthropic, "Demystifying evals for AI agents", Jan 2026). Neither number tells you whether the harness can fix your backlog.

Anthropic's guidance is specific: 20 to 50 simple tasks drawn from real failures is a great start, because early changes have a large effect and small samples suffice (same post, Step 0). An ambiguous task becomes noise in the metric.

What you get in week one is a number that survives an argument. Before the suite, "the agent feels worse" is an opinion. After it, a regression is a red build.

Signals: pass@1 is Anthropic's definition — the fraction of tasks solved on the first try. Cost per success is the metric Anthropic tracks as "cost per task". False completion is documented directly in the SWE-bench post: the model cannot see the grading tests, so it often "thinks" it has succeeded when the task actually failed. Review minutes is our own metric; no external source for it, treat the number as illustrative.

The gate is the whole point. If a harness change lowers pass@1, it does not merge.

Harness that verifies

Pays in review minutes, now.

~1:00. Three costs. Only one of them appears on the invoice.

Tokens: context assembly and memory retrieval are re-sent on every turn. The arithmetic on screen is 6,000 tokens per turn times 20 turns — 120,000 input tokens per task. Both inputs are illustrative, not a published measurement. At Claude Sonnet 5.5's $2 per million input tokens that is $0.24 per task. The same tokens served as cache reads at $0.10 per million cost $0.012 (Anthropic API pricing page, read 24 Oct 2026). Caching is a harness feature, not a billing trick.

Latency: every extra model call and tool round trip is serial. One verifier call that prevents five turns of rework pays for itself. A retriever that blocks every turn does not.

Review: a harness that verifies charges minutes at the diff. A harness that does not charges incident time later. Anthropic's evals post describes teams without evals as stuck in a loop: fix one failure, create another, find out in production.

The bottom line is sourced: Anthropic states that SWE-bench Verified performance "can vary significantly" with the scaffolding, on the same model. The line in the review tab — a cheap model with a good harness beats an expensive model with a bad one — I could not source as a measured comparison. It is labelled opinion on the slide, and it is opinion.

Measure cost per successful task, not cost per call. Next: where the harness is allowed to act.

~1:15. Four tiers, in the order you should grant them. Read only comes first, always.

Write inside the repo is tier two. OpenAI's Codex calls this workspace-write and describes it as the default low-friction mode: the agent reads and edits inside a boundary, and routine commands run there without a prompt. When a task needs to go beyond the boundary, the approval flow takes over (OpenAI Codex sandbox documentation).

Execute is where the blast radius jumps. Claude Code's manual mode starts read-only and asks before edits or commands; unmatched commands require approval by default, and an allow rule for part of a command does not skip the prompt (Anthropic, Claude Code security documentation). Put the approval gate on irreversible actions only: migrations, deletes, force-push, deploys. Approving everything trains people to click yes.

Network last, and never as a blanket "internet on". Claude Code's cloud sessions limit network access by default and can allow only specific domains; its local sandbox isolates bash commands at the filesystem and network level.

The callout is the part leadership needs. OWASP LLM01:2025 defines indirect prompt injection as instructions arriving through websites or files, and states that fool-proof prevention is unclear. Its mitigations are privilege control, least privilege, human approval for high-risk actions, and segregating untrusted content. OWASP LLM06:2025 names the root cause of excessive agency: excessive functionality, excessive permissions, excessive autonomy. None of that is fixed by a better prompt.

So untrusted text never carries instructions. A README, an issue body, a web page, a test failure: all data. If any of them can issue orders, the agent is a confused deputy.

~1:00. Ownership is the difference between a demo and infrastructure. Without one, the prompt grows, the tool list grows, and nobody can say whether quality moved.

Anthropic's evals guidance, "Demystifying evals for AI agents," reports that a suite stays useful only with ownership: an eval suite is, in their words, "a living artifact that needs ongoing attention and clear ownership to remain useful." They found dedicated evals teams owning the core infrastructure works, with product teams contributing the tasks.

Platform engineering's "What is platform engineering?" makes the same point: start with a small minimum viable platform, not a department. The smallest viable team here is two people, part time; a third makes it durable. A harness engineer and an eval owner run the loop. The product owner picks the first workflow. Security review is borrowed for the trust boundary, because Anthropic's "Trustworthy agents in practice" says a well-trained model can still be exploited through "a poorly configured harness, an overly permissive tool, or an exposed environment."

One change per run, or you learn nothing.

~1:00. This is ordinary engineering discipline applied to a probabilistic system. Anthropic's "Demystifying evals for AI agents" defines a transcript, or trace, as "the complete record of a trial, including outputs, tool calls, reasoning, intermediate results, and any other interactions," and says reading transcripts is how you verify the eval measures what matters.

Hamel Husain's "Your AI Product Needs Evals" makes logging traces the prerequisite, then says to remove all friction from looking at them. Pick the failure, name which harness part caused it, change that one part, rerun the same suite.

One change per run: change two and a pass tells you nothing about which one worked. Keep the change only if the suite moves; otherwise revert it and name the next cause. Traces are the spec.

What the first thirty days look like.

  1. Week 1

    Twenty real tasks. Pass or fail, by hand.

  2. Week 2

    A full trace of every run.

  3. Week 3

    One verification step. One scoped tool set.

  4. Week 4

    The suite in CI. A regression gate.

  5. Ongoing

    One named owner. A weekly trace review.

~1:00. Month one is measurement, not modernization. Anthropic's "Demystifying evals for AI agents" says to start with "20-50 simple tasks drawn from real failures," and to keep regression evals at "a nearly 100% pass rate."

Week 1 is manual on purpose: you are learning the failure modes, not building tooling. Week 2 makes every run inspectable, because a failure you cannot replay is a rumor. Week 3 changes the harness: one verification step, and a tool set scoped to the task.

Week 4 moves the suite into CI so the gate runs on every commit, which Anthropic lists as a property of automated evals. Then keep one named owner and a weekly trace review.

Skip new models, new frameworks, and fine-tuning in month one. With no baseline you cannot attribute the change. Anthropic notes that teams without evals face weeks of testing when a new model lands, while teams with evals upgrade in days.

05 · Team and process

How harness work goes wrong.

The tell

Your score climbs. Production does not.

The harness learned the tasks, not the work.

The countermeasure

Hold out ten tasks. Rotate them each quarter.

Report the held-out number, never the tuned one.

The tell

Every incident adds a paragraph. The rules start to cancel out.

Nothing is wrong with any single line.

The countermeasure

Prune to rules that change behavior. Move hard rules into hooks.

Hooks are deterministic; prose is advisory.

The tell

The failure leaves the dashboard. The bug stays in the product.

The suite is green because the suite was edited.

The countermeasure

Grade on a check the agent cannot edit.

Then read the trace, not the summary.

The tell

One private harness beats the team's. Nobody can reproduce it.

It skips the review path everyone else uses.

The countermeasure

Check the harness in. Every run lands as a reviewed diff.

Same tasks, same tools, same review.

~1:00. Each of these looks like progress for a month, then stops paying.

Overfit. SWE-Bench+ (Aleithan et al., 2024) re-checked the top agent's passing patches: 32.67% had the fix leaked in the issue, 31.08% passed on tests too weak to prove correctness. After removing those tasks the resolve rate fell from 12.47% to 3.97%. Your twenty tasks can do the same thing to you.

Sprawl. Anthropic's Claude Code guidance: if CLAUDE.md is too long, Claude "ignores half of it because important rules get lost in the noise." Prune, then turn hard rules into hooks, which run deterministically instead of advising.

Hiding failure. METR (June 2025) reports frontier models "attempting (often successfully) to get a higher score by modifying the tests or scoring code." Anthropic's long-running agent harness keeps its feature list in JSON, and its prompt says it is "unacceptable to remove or edit tests because this could lead to missing or buggy functionality." The check has to sit outside the agent's write scope.

Shadow harness. GitHub's cloud agent works in a branch and opens a pull request, and its docs say session logs "do not replace your own review and testing." A private stack on one laptop skips exactly that path.
